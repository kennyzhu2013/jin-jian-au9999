# Au9999 历史日线本地保存与增量维护 — 实施方案

> 目标：少打上金所历史接口；接口挂了仍有可用 K 线；实时价继续走极速转发。  
> 范围：`jinjian-quote-proxy`（服务端权威）+ 金鉴 PWA（端上兜底，可选二期）。  
> 日期：2026-10-19（Asia/Shanghai）

---

## 1. 结论（是否可行）

**可行，且建议做。**

现状问题：

- Vercel Serverless 进程内缓存（约 3 小时）在冷启动会丢，仍会反复打上金 `Dailyhq`。
- 上金公开接口无 SLA，偶发超时 / 风控 / 页面改版都会让 `bars` 变空或失败。

方案核心：

1. **服务端持久化一份「已清洗日线」**（权威源）。
2. **优先读本地；定期或按需才回源上金。**
3. **盘中用极速实时价维护「当日 bar」**；收盘后定格，隔日再开新 bar。
4. 上金不可用时：**照样返回本地 bars + 实时 quote**，并在 `note` 标明数据来源。

---

## 2. 数据角色分工

| 数据 | 来源 | 用途 |
| --- | --- | --- |
| 实时 `quote` | 极速 `shgold`（已有） | 现价、开高低、昨收、提醒 |
| 历史 `bars`（D1） | 上金 `Dailyhq`（回源）+ 本地库 | 策略、图表 |
| 当日未收盘 bar | 由 `quote` 增量维护 | 减少盘中回源；断档补洞 |

金鉴端只消费转发结果，**不必直接打上金**。

---

## 3. 推荐架构（一期：只改转发，应用地址不变）

```
金鉴 App
  │  GET 自定义行情 URL（不变）
  ▼
jinjian-quote-proxy /api/quote
  ├─ 极速 → quote（每次或 30s 缓存）
  ├─ 读持久化 bars（Vercel Blob / KV）
  ├─ 必要时回源上金 Dailyhq → 清洗写入
  └─ 用 quote  upsert 当日 bar → 合并返回
```

**一期不改** `https://jinjian-quote-proxy.vercel.app/api/quote` 的对外路径与字段约定；金鉴设置不用改。

### 3.1 持久化选型（按简单程度）

| 选项 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- |
| **A. Vercel Blob** 存 `au9999-bars.json` | 实现简单；与现有项目同账号；文件可读 | 需处理并发写 | **一期首选** |
| B. Vercel KV / Redis | 读写快；易做锁 | 多一个产品/配置 | 二期若 QPS 升高再换 |
| C. 写回 Origin / Git | 可审计 | 不适合盘中高频写 | 不做主路径 |
| D. 仅 PWA IndexedDB | 离线友好 | 多端不同步；不是权威 | **二期端上兜底** |

一期：**Blob 一份 JSON（权威）** + 进程内短缓存（减读费用）。

### 3.2 存储文件格式（示例）

路径建议：`gold/au9999-bars.json`（Blob）

```json
{
  "symbol": "Au99.99",
  "updatedAt": "2026-10-19T11:20:00+08:00",
  "sourceLastOk": "2026-10-16",
  "sgeLastFetchAt": "2026-10-19T02:00:00+08:00",
  "sgeLastFetchOk": true,
  "bars": [
    {
      "date": "2026-10-16",
      "open": 893.99,
      "high": 902,
      "low": 893,
      "close": 901.57,
      "source": "sge",
      "final": true
    }
  ]
}
```

约定：

- `final: true`：已收盘定格，**禁止**再用实时价改 OHLC（除非人工校正）。
- `final: false` 或无该字段：当日进行中，可用实时价更新 high/low/close。
- 保留最近 **250～500** 根（约 1～2 年交易日），超出从头部裁剪；对外仍可只吐最近 120 根给金鉴（与现网一致）。

## 4. 读写与回源策略

### 4.1 每次 `/api/quote` 流程

1. 拉极速 → 得到 `quote`（失败则 502；有本地 bars 时可降级「仅 bars」，一期可不做）。
2. 读本地 bars（先内存 → 再 Blob）。
3. **是否回源上金**（满足任一才打）：
   - 本地为空 / 损坏；
   - 距上次成功回源 ≥ **24 小时**（建议放在凌晨 0:30–6:00 Asia/Shanghai，避开交易高峰）；
   - 本地最新 `final` 日距「上一个交易日」缺 1 天以上（缺日补洞）；
   - 管理接口强制刷新（见 §6）。
4. 回源成功：合并（以上金为准覆盖同日期）、标 `final: true`、写回 Blob、更新 `sgeLastFetch*`。
5. 回源失败：**不报错打断**；沿用本地；`note` 加「日线缓存 / 上金暂不可用」。
6. **用 `quote` 维护当日 bar**（§5）→ 写回 Blob（可节流，见下）。
7. 返回金鉴 JSON：`quote` + `bars`（ascending）+ `note`。

### 4.2 写回节流（减 Blob 写入）

- 进程内：当日 bar 每 **1～5 分钟**最多写 Blob 一次；或 close 变化 ≥ **0.5 元** 才写。
- 内存始终最新，保证同实例响应一致。

### 4.3 并发

- 多实例同时写 Blob：采用「读 → 改 → 覆盖写」可接受短期轻微覆盖；或写入带 `updatedAt`，只接受更新的版本（乐观锁）。
- 一期可接受最终一致；不必上分布式锁。

## 5. 用实时价维护当日 K 线（核心）

交易日判定（Asia/Shanghai）：

- 建议简化：周一至周五，且不在已知休市列表（一期可用「工作日」近似；二期可接节假日表）。
- 上金夜盘跨日时：以**交易所日线归属日**为准；若与极速 `updatetime` 的日历日不一致，**优先沿用上金已有规则**——一期可约定：当日 bar 的 `date` = 上金惯例交易日（若拿不到，则用 `quote.time` 的上海日期，并在 note 说明）。

算法（已有当日未 `final` 的 bar，或新建）：

```
open  = 已有 open；若无则用 quote.open 或 quote.price
high  = max(已有 high, quote.high, quote.price)
low   = min(已有 low,  quote.low,  quote.price)  // 忽略 0 / 无效
close = quote.price
source = "sge+live" 或 "live"
final = false
```

收盘定格（二选一，建议都做）：

- **A. 定时**：每个交易日 **15:35**（上海）后，把当日 bar 标 `final: true`（可用 Vercel Cron 调 `/api/cron/finalize`）。
- **B. 回源覆盖**：次日凌晨回源上金成功后，用官方日线覆盖同日并 `final: true`（权威校正）。

这样：上金短暂不可用时，图表与策略仍有「近似真实」的当日与历史序列。

## 6. 接口规划

| 路径 | 作用 | 访问控制 |
| --- | --- | --- |
| `GET /api/quote` | 对外唯一消费口（金鉴） | 公开（现状） |
| `GET /api/bars/meta` | 查看条数、最新日、上次回源时间（调试） | 可选加简单 token |
| `POST /api/bars/refresh` | 强制回源上金并写库 | **必须** `Authorization: Bearer <CRON_SECRET>` |
| `POST /api/cron/finalize` | 收盘定格当日 bar | 同上；给 Vercel Cron |

环境变量新增：

- `JISU_APPKEY`（已有）
- `BLOB_READ_WRITE_TOKEN`（或项目已绑定的 Blob）
- `CRON_SECRET`
- 可选：`BARS_MIN_COUNT=120`、`SGE_REFRESH_HOURS=24`

## 7. 与金鉴 App 的关系

### 一期（推荐先做完）

- App **零改动**，继续指向现有自定义行情 URL。
- 所有持久化与降级在 proxy 完成。

### 二期（可选端上兜底）

- 金鉴把最近一次成功的完整 feed 存 **IndexedDB**。
- 自定义接口失败时：用本地 feed + 提示「离线行情」。
- 不替代服务端权威库，只防手机侧断网。

---

## 8. 实施步骤与工期（粗估）

| 阶段 | 内容 | 预估 |
| --- | --- | --- |
| P0 | Blob 读写封装；启动时若空则回源灌入；`/api/quote` 改「本地优先」 | 0.5～1 天 |
| P1 | 当日 bar 用 quote 增量维护 + 写回节流；失败降级 note | 0.5 天 |
| P2 | Cron：日终 finalize + 每日凌晨 refresh；`CRON_SECRET` | 0.5 天 |
| P3 | `bars/meta`、监控告警（连续 N 次回源失败推送你） | 0.5 天 |
| P4 | （可选）金鉴 IndexedDB 兜底 | 0.5～1 天 |

验收标准：

1. 人为让上金请求失败（或断网模拟）时，`/api/quote` 仍返回 ≥120 根历史 + 有效实时价。
2. 连续交易日无强制回源时，Blob 中当日 high/low/close 随极速更新。
3. 次日回源后，昨日 bar 与上金官方 OHLC 一致（允许极小误差，以官方覆盖为准）。
4. 一周内上金请求次数 ≪ 现在「按访问 / 冷启动」频率（目标：约每天 0～1 次成功回源）。

## 9. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 实时维护的当日 OHLC ≠ 官方日线 | 次日回源强制覆盖；策略重要信号以 `final` bar 为主 |
| Blob 写入冲突 | 节流 + 乐观锁；可接受分钟级覆盖 |
| 节假日误开 bar | 二期加休市表；一期靠次日回源纠正 |
| Blob / Cron 费用 | 日线 JSON 很小（几十 KB）；Cron 每天 1～2 次可忽略 |
| 密钥与管理接口 | refresh/finalize 必须带 secret；勿把 secret 写进前端 |

---

## 10. 明确不做（一期）

- 不换成聚合数据当历史源（无可用 AU9999 历史 API）。
- 不把极速 `appkey` 放进金鉴前端。
- 不做分钟线 / Tick 落库（除非另开需求）。
- 不保证「投资建议」合规口径以外的实时成交价权威性——展示与策略辅助用。

---

## 11. 建议落地顺序（你确认后我按此改代码）

1. **P0 + P1**：本地优先 + 实时维护当日 bar（收益最大，地址不变）。
2. **P2**：Cron 收盘定格与凌晨回源。
3. **P3**：可观测性（失败才推送）。
4. 需要离线再开 **P4**。

确认「按该方案实施」后，直接从 P0 改 `jinjian-quote-proxy` 并重新部署即可。
